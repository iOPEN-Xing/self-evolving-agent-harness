# 第 04 章：将一次纠正变成有范围的项目规则

上一节：[上下文装配](../03-context-engine/README.md) · 下一节：[上下文压缩](../05-context-compression/README.md)

## 从对话纠正到可复用约束

某次支付事故里，用户纠正了“先发生变更就一定导致告警”的推断。新 Thread 不自动继承旧对话。若这种要求适用于后续项目任务，应存成项目规则，并明确加载范围。本章用 `AGENTS.md` 比较旧纠正、根规则和局部规则。

## 案例怎样形成对照

先在旧 Thread 分析事故并接收纠正，再把另一场事故交给全新 Thread，不写规则。检查新请求有没有旧纠正，而不是预设模型一定再次犯错。模型原本就谨慎的运行同样有效，不能为了展示收益把它判为错误。

随后把因果判断规则写在 `WORK/AGENTS.md`，把支付服务特有的核对要求写在 `WORK/payment-service/AGENTS.md`。用同一新事故分别在根目录和支付服务目录创建 Thread，检查根目录只加载根规则、服务目录加载两级规则的实际情况。

## 代码与运行

入口：[workshop.ipynb](workshop.ipynb)。环境准备后，从根目录执行：

```bash
.venv/bin/python -m jupyterlab examples/04-agents-md/workshop.ipynb
```

| 单元 ID | 作用 | 要核对的对象 |
|---|---|---|
| `lab04-reader-03` | 生成旧、新事故及同一句纠正 | 对照条件、两个工作目录 |
| `lab04-reader-05` | 旧任务纠正、无规则新任务 | 新请求是否自动继承纠正 |
| `lab04-reader-07` | 写两级规则并建新 Thread | 根、局部规则在真实请求中的位置 |
| `lab04-reader-09` | 可选撤下局部规则 | 新 Thread 的规则变化 |

`Lab.thread(cwd=...)` 先检查目录属于本次实验，再交给 SDK。默认只读任务，准备区的规则文件由课程代码写入。`RUN_REMOVE_LOCAL=False` 默认不运行；启用后撤下并恢复规则文件，不据此推断旧 Thread 会实时刷新配置。

## 如何设计可落地规则

根规则适合项目通用约束：区分事实与猜测、引用时间窗、避免虚构执行结果。局部规则适合支付服务的字段、入口和限制。规则应短而明确，说明触发条件与优先级；完整业务步骤更适合 Skill，现场事实更适合工具返回或 Memory。

规则进入请求与判断正确是不同层次。`AGENTS.md` 不能给输入目录加写保护，也不能代替审批。生产接入应给规则保留版本、负责人、适用目录和冲突处理方式，规则变更之后用固定样例重新核对。

## 失败分支与练习

规则未出现时先检查 `cwd`、文件位置和新 Thread 建立时点；出现了却没被遵循时，再检查表述冲突、任务上下文与评测。不能单靠最终回答提到“谨慎”判定规则已经加载。

为另一个服务新增局部要求，分别从根目录与服务目录运行同一任务。正确的验证先比较输入中的规则，再比较判断；若回答没变化，只能说明本次没呈现行为差异，不能直接宣布规则无效或有效。
