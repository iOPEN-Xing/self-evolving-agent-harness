# 第 02 章：给活跃任务补充告警，或中断它

上一节：[Agent Loop](../01-agent-loop/README.md) · 下一节：[上下文装配](../03-context-engine/README.md)

## 从固定目标到执行中控制

上一章提交目标后等待结束。值守时可能在巡检过程中收到新告警：需要将信息交给当前任务，而不是等旧任务结束再开一次无关调查。本章比较 `steer()` 与 `interrupt()`。前者追加活跃 Turn 的输入，后者请求中断；它们都不自动回滚已经产生的副作用。

## 案例与观察条件

构造的巡检包括 `server-17/payment-api` 与 `server-31/order-api`。支付服务器有部署和日志材料，订单服务器随后检查。脚本设置约 25 秒慢探针，给告警留出窗口，并要求独立 `cat` 读取，便于把命令和回执逐个配对。这些是实验条件，生产巡检不应为了展示过程人为等待。

告警不能随意在启动后立即提交。代码先确认支付服务器的两份材料都有成功回执，随机标记确实在工具输出中，并且慢探针仍在运行，才调用 `steer()`。如果窗口已消失，本次不满足观察条件，应记录失败并重跑，不能把新 Turn 的结果当作执行中控制。

## 代码与运行过程

入口：[workshop.ipynb](workshop.ipynb)，校验：[control_validation.py](control_validation.py)。先完成环境准备，在仓库根目录执行：

```bash
.venv/bin/python -m jupyterlab examples/02-instruction-control/workshop.ipynb
```

| 单元 ID | 作用 | 核查重点 |
|---|---|---|
| `lab02-reader-03` | 材料、慢探针、事件和校验函数 | 输入标记属于本次运行 |
| `lab02-reader-07` | 启动巡检、等待条件、提交告警 | 同一活跃 Turn 收到新输入 |
| `lab02-reader-09` | 展示巡检时间线与报告 | 告警后调查及恢复巡检是否真实发生 |
| `lab02-reader-11` | 新建 Thread 执行中断对照 | 中断状态和探针实际进程状态分别看 |
| `lab02-reader-13` | 清理连接和探针 | 再次运行创建新目录 |

`control_validation.py` 按调用编号和工具输出判断读取、调查与恢复，不能只搜索模型回答里的“已检查”。SDK 调用仍走官网原生 Responses；外部工具回执保持 Responses 语义，不转换成普通用户指令。

## 三种事件要分清

| 事件 | 改变什么 | 不应推出什么 |
|---|---|---|
| `steer()` 被接受 | 当前 Turn 获得补充信息 | 任务已正确处理告警 |
| 后续工具调查并有回执 | 已执行相应查询 | 故障已恢复或根因已证实 |
| `interrupt()` 后状态结束 | 当前模型任务结束 | 子进程、外部事务和文件副作用已回滚 |

中断对照是另一条新 Thread，不依赖前面的报告。只看 `interrupted` 不足以证明底层命令已停止；要检查探针标记和清理结果。正文中的 stop 表示停止后续循环或调度，具体框架接口需单独核对。

## 失败处理与落地

材料读取失败、未达到慢探针窗口或事件缺少恢复步骤，均保留真实记录。失败后不向旧 Turn 反复投递告警；执行清理格，再创建新运行。SDK 的任务取消与 OS 进程组回收是两层机制，工程实现需要分别负责。

将此模式接到告警平台时，应携带告警 ID、对象、时间窗、优先级和去重状态，区分“已接收”“已调查”“已解决”。不要让一条补充消息隐式扩大操作权限。需要取消的工具应支持独立句柄、期限和结果状态。

## 练习

缩短探针时间，观察条件检查怎样阻止错误演示。再找出一条告警投递后的实际查询回执，解释它能证明的范围；如果没有恢复巡检证据，报告应写“未观察到”，而非补上预期步骤。
