# 第 01 章：从一条 500 告警读懂 Agent Loop

上一节：[环境准备](../../docs/MODEL_SETUP.md) · 下一节：[执行中控制](../02-instruction-control/README.md)

## 要解决的问题

凌晨支付接口出现 500，输入只有告警、日志和一段业务代码。我们需要可核查的调查报告。Agent Loop 把目标、模型选择的动作、工具返回和后续判断连起来；一次模型回答并不等于完成调查。本章先建立这个最小闭环，后面再讨论如何控制它、如何保存经验。

## 用同一请求串起三个证据

Notebook 第 5 格生成构造材料：`inputs/alert.md` 指出 02:07、`POST /checkout`、8.4% 错误率和 `req-7f3a`；`logs/payment-api.log` 记录该请求只有 `amount=29900`，随后发生 `KeyError: 'currency'`；`src/checkout.py` 直接访问 `payload["currency"]`。这些文件是教学输入，不是生产采集结果。

合理的调查链是：用请求编号定位错误，用堆栈定位代码，再说明缺少字段与异常的联系。它能支持“样例请求因缺失 currency 触发异常”的判断，不能仅凭一个样例解释全部 8.4% 失败，也不能证明哪个客户端或发布引入了缺失字段。修复建议应与已证实故障范围分开。

## 代码与运行过程

入口：[workshop.ipynb](workshop.ipynb)，共用实现：[Lab](../notebook_support.py)。先完成环境准备，在仓库根目录启动：

`workspace_write` 允许在工作目录写报告，`deny_all` 拒绝扩权。任务只规定材料范围和产物，未规定读取顺序。模型可能一次读取多个文件，不能把合并读取描述为逐步发现。`Lab.run` 等待 Turn 并检查最终状态；工具执行、报告存在、报告正确是三个不同的检查。

## 怎样判断实验完成

沿本次 `.runtime/<run_id>/` 的请求和 Turn 记录回查：Agent 是否实际读到告警、日志和代码；报告中的行号、请求编号与原文是否对应；是否明确写出样例范围和未决问题。输入哈希不变只证明本次运行没有改动输入，不能证明执行时存在目录级写保护。

文字中的“不要修改输入”仍是模型规则，整个工作目录的可写权限更大。第 09 章会把输入与输出分成不同权限范围。不要据本章推断可安全连接生产数据库或自动修复支付接口。

## 从动作与观察理解循环

可以把一轮看成：模型根据当前材料提出动作，Harness 执行获准工具，将观察送回模型，模型据此继续或结束。模型生成的是动作建议，工具返回才是本次环境观察；Harness 还负责把失败、退出码和停止状态保留下来。若只保存最终报告，下一次复盘就无法区分读错对象、工具失败和推断错误。

样例中的因果依据不是‘告警之后读到错误’，而是同一请求的 payload、异常堆栈和直接取字段的代码互相对应。扩大到全部错误率前，还需要其它失败请求及正常请求作对照。工程上先建立对象与时间的一致性，再评估结论，最后考虑动作权限。

## 在学习循环中的作用

自进化首先需要可靠的经历：当时收到什么输入、模型请求了什么工具、工具实际返回什么。本章建立这条可观察的执行链；后续复盘应读取这些材料，再判断哪些内容值得保存为方法。

## 面试讲述与追问

我的关注点是支付告警能否形成可核查的调查链。我用请求编号把日志中的缺字段异常与代码访问位置连起来，让模型选择读取动作，工具提供实际观察。相比直接让模型猜根因，这样可以回查每个结论的来源。样例能解释这一条请求为何失败；整批 8.4% 错误的共同原因仍需更多请求和同时间窗数据。

**追问：读取了三个文件，为什么还不能证明整个告警的根因？** 三份材料围绕同一个请求，扩大的是该请求的证据链，没有扩大失败样本覆盖。应按请求分组检查相同堆栈、缺字段比例与发布时间，再决定能否推广这个解释。

讲述时可打开 [workshop.ipynb](workshop.ipynb) 核对实现或原始记录；个人贡献与结果的表述规则见 [项目面试指南](../../docs/INTERVIEW_GUIDE.md)。

## 失败分支与工程应用

若读文件失败，保留回执而非继续编造结论；若 Turn 超时或中断，报告即使存在也可能只是部分产物。报告有内容时继续检查依据，不能只按文件大小验收。模型连接问题先按环境准备页排查。

落地时把“原始观察 → 证据引用 → 判断 → 未决事项”作为报告协议，为每个工具调用保留编号、参数、退出状态和输出来源。读日志与执行变更应是不同工具权限。先从只读调查开始，待证据和验收稳定后再引入受控操作。

## 练习

把某个日志请求编号改成不匹配，重跑并观察模型是否指出缺口。正确验收是“不再把两份不对应记录连成已证实因果”，不是仍然生成原来的根因。再对照两次工具顺序，说明哪些步骤是模型选择，哪些由 Harness 固定。
