# 第 05 章：压缩任务状态，保留回查原文的能力

上一节：[项目规则](../04-agents-md/README.md) · 下一节：[会话分支](../06-thread-fork/README.md)

## 长任务遇到的两个问题

日志不断进入上下文，既增加输入长度，也可能淹没目标、纠正和操作限制。压缩应保留任务状态，但摘要很难保留每个原始数值。本章观察原生压缩事件，并区分当前模型输入、完整会话历史与磁盘原文。

## CASE-527：计划保留，采样细节回查

准备区生成 180 行 `capacity.log`：CPU 24%、内存 41%，每条 `elapsed_us` 随机生成。末尾有连接等待 3600ms、占用 60/60 和池上限 60。用户随后确认 CPU 正常、排除 CPU 饱和猜测，要求先核对池配置且不得重启。

压缩后先让 Agent 不调用工具，复述编号、目标、排除项、下一步和限制；再追问 `sample=0073` 与 `sample=0127` 的耗时与差值。数值每次不同，应以本次日志为准。追问没有重发原文或指定命令，用新增工具回执观察它是否发现缺口并回查。

## 代码与运行

入口：[workshop.ipynb](workshop.ipynb)。环境准备后运行：

```bash
.venv/bin/python -m jupyterlab examples/05-context-compression/workshop.ipynb
```

| 单元 ID | 动作 | 验证边界 |
|---|---|---|
| `lab05-reader-03` | 生成日志；定义 `wait_compaction` | 等待新增 `contextCompaction` Turn，最多 240 秒 |
| `lab05-reader-05` | 读取日志、接收纠正 | 压缩前请求和历史作为对照 |
| `lab05-reader-07` | `thread.compact()` 并等完成 | 接口返回不代表压缩已完成 |
| `lab05-reader-09` | 复述状态、追问采样值 | 当前输入、历史、磁盘和新增工具回执分别看 |

`wait_compaction` 排除压缩前已有 Turn，只接受新增压缩事件的 completed 状态。失败或中断不能继续声称状态已保留。`command_receipts` 按调用编号去重，避免把历史重复携带误算成重新读文件。

## 怎样评估压缩

先检查摘要里的五项任务状态，再核对采样数值是否与原文一致。原句不在输入中不代表事实一定丢失，可能被改写；原句存在也不证明推理正确。Notebook 只做事件、原句、字符数和文件变化观察，没有自动实现任务状态与数值结论的完整语义评分。

字符数可能下降，也可能因摘要与规则而上升，不能把字符差直接称为 token 节省。完整 Thread 历史还能取到旧消息，不等于下一次请求仍发送全部旧历史。磁盘保存原文提供回查来源，但能否正确找到所需行取决于工具和模型。

## 摘要为什么应保留状态而非全部原文

压缩需要选择保留信息。目标、排除项、未决问题和禁止动作决定下一步是否仍正确；大量采样数值更适合保留原始来源与定位方式。把未知写成已确认，或把禁止重启遗漏，比丢掉一条可回查的采样数值更危险。

因此本例分两类追问：先问任务状态，再问具体数值。前者检查调查能否继续，后者检查原文是否仍可取得。只有回查工具成功、数值对应本次日志、计算正确，才支持细节恢复；完整历史可读只是一个可用来源，并不能保证下一次请求会自动包含它。

## 在学习循环中的作用

压缩维护的是当前调查的可用上下文。它让经历在长任务中可继续读取；提炼可跨任务复用的 Skill，还需另作内容选择、验证与版本决定。不要将摘要长度变化解释为方法能力的提升。

## 工程应用与练习

长时间调查应把目标、已确认事实、已排除假设、待查项、操作限制、证据地址写入状态摘要；把大量原文留在可检索存储，必要时重新读取。压缩前后用固定任务追问验证，而不是只量输入长度。

删掉日志中的目标采样行再重跑。合理结果应指出缺失并停止猜值。另检查 Agent 若没有回查，是摘要已含数值、回答失败，还是工具没有执行；这三种情况不能合并成“压缩可自动恢复全部细节”。
