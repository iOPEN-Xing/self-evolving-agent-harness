# 第 03 章：文件存在，何时才成为模型的依据？

上一节：[执行中控制](../02-instruction-control/README.md) · 下一节：[项目规则](../04-agents-md/README.md)

## 要解决的问题

Agent 能访问文件，不代表模型已经读过。上下文装配决定每次请求里有哪些目标、规则、历史、工具定义和返回。本章固定同一个问题，比较读取部署记录前后，先学会观察输入，再评价回答。

## 同一问题的两次现场

告警只有“02:07 payment-api P95 超过 3 秒、5xx 达 8.4%”。磁盘 `deployment.md` 另写入“01:40 连接池上限从 200 调至 60，是否导致告警待核对”，带本次随机采集编号。

第一次明确禁止工具，只问已确认事实和缺失信息。模型只能依据告警。第二次在同一 Thread 先读取部署记录，再回答同一问题。变更与异常的时间关系是新增事实；没有同时间窗连接指标、负载和下游信息时，仍不能宣布已经证明变更是根因。

## 代码与运行

入口：[workshop.ipynb](workshop.ipynb)，共用请求观察：[notebook_support.py](../notebook_support.py)。环境准备后，从根目录执行：

```bash
.venv/bin/python -m jupyterlab examples/03-context-engine/workshop.ipynb
```

| 单元 ID | 动作 | 证据 |
|---|---|---|
| `lab03-reader-05` | 生成部署记录；两次 `run` | 初次请求、读文件回执、读取后回答 |
| `lab03-reader-07` | 展开每次 Responses 请求 | `instructions`、`input`、`tools` 中的实际内容 |
| `lab03-reader-09` | 同一 Thread 再问；可选新 Thread | 历史工具结果是否仍进入请求 |

本机观察服务记录请求的教学字段，不保存认证头，随后原样转发到 DeepSeek 官网。它显示 Harness 发出的输入，无法查看模型内部状态，也不能把请求里的每句话都解释成模型已经正确理解。

## 用标记与回执验证加载

随机标记只写在文件里。若它在读取前的输入中不存在，在成功工具回执及后续请求中出现，可以说明这次文件内容经由工具进入上下文。检查工具回执比搜索最终回答可靠：模型可能不复述标记，也可能根据用户提示猜测文件内容。

Notebook 随后只追问已知事实，不重发原文，观察同一 Thread 的首次请求是否保留历史。`RUN_NEW_THREAD=False` 的可选对照改为 True 后，新任务不自动继承旧 Thread 消息；但项目规则与磁盘仍可能共享，需要分别检查。

## 在学习循环中的作用

新方法是否落盘与是否进入模型输入是两个检查点。本章用请求记录观察加载，为后续 Memory 召回和 Skill 采用提供验证方式：更新之后，要继续核对任务实际看到了哪份内容。

## 工程价值与边界

RAG、Memory 或 Skill 接入也适用这一检查方法：先验证召回对象、来源和装配位置，再判断内容是否改变决策。把“有权限访问”“已召回”“已装配”“回答正确”拆成独立状态，能快速定位问题属于工具、检索、装配还是业务判断。

输入字符数是文本长度，不是 tokenizer 计数或费用。文件哈希未变化支持本次只读观察，不证明所有动作受到了强制隔离。若工具失败，后续回答应保留缺口，不应把磁盘中存在的变更自动写成已知事实。

## 练习

在读取前只修改部署记录，保持告警不变。两次首轮输入是否变化？再只修改工具读取路径，检查失败回执是否影响后续回答。解释为什么两条回答文字相近仍不能证明它们读过相同材料。
