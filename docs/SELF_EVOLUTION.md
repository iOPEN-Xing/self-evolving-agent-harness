# 自进化如何发生：从经历到下一次执行

本仓库把自进化落在可版本化的方法上：Agent 根据执行经历生成 Skill 候选，Harness 依据事先约定的业务检查决定是否更新，后续任务再使用实际采用的方法。模型负责提炼与执行，控制器负责候选隔离、验证和版本切换。这种分工让经验能够改变后续行为，同时保留明确的失败出口。

本文以 [原生支付 Capstone](../examples/capstone/README.md) 为主线，沿当前代码解释闭环。前九章建立执行与观察能力；[第 10 章](10-learning-loop.md) 衔接后半程；各章节在闭环中的位置见文末。当前真实运行覆盖另见 [验证记录](DOCUMENTATION_VALIDATION.md)，本文中的预期分支与教学算例不作为新的联网结果。

## 1. 系统到底改变什么

| 对象 | 本仓库怎样处理 | 对下一次任务的作用 |
|---|---|---|
| Session | 保存任务、模型消息、工具请求与回执 | 提供可回查的经历与修订依据 |
| Memory | 保存或纠正有适用条件的事实、偏好 | 改变后续召回的事实条件；使用效果须单独观察 |
| Skill | 更新调查步骤、判断条件和支持文件 | 新任务加载不同的方法，执行路径可能随之变化 |
| 模型、工具、评分器与采用规则 | 在一次对照中保持执行协议固定 | 提供可比较的基准及变更边界 |

本项目演示的方法学习发生在 Skill 内容层。模型权重训练、Harness 源码自动修改、评分器自动改写不在这条主线中。第 12 章的明确事实纠正、第 17 章的生命周期整理、第 18 章的手写指令对照分别验证其中一部分关系。

可以把一轮更新写成以下概念式：

```text
经历 = 执行(当前任务, 当前方法)
候选 = 复盘(经历, 当前方法)
决定 = 验证并比较(当前方法, 候选, 固定任务与评分条件)
下一版方法 = 候选，若决定为 ADOPT；否则保留当前方法
下一次结果 = 执行(下一任务, 实际加载的下一版方法)
```

最后一行把更新接回在线执行。只有生成文件时，我们只能说“有了候选”；接收端执行时的方法和工具回执，才说明这次更新走到了使用环节。

## 2. 一笔订单怎样成为可复用方法

主线输入来自 [orders.json](../examples/assembly/scenarios/orders.json)。ORD-A2 应付 800，TXN-X 的 `status` 为 `processing`，`channel_acceptance` 为 `success`。这两项合在一起表示渠道已受理、尚未最终到账。学习任务还通过用户提示给出内部规程：满足这组条件时进入 `payops-confirm-17`；规程正文由 [run_skillclaw_demo.py](../examples/assembly/run_skillclaw_demo.py) 的 `POLICY` 提供。

这里有两类来源：支付工具返回交易状态，用户提示提供组织规程。Agent 要把它们组合成有条件的方法，不能仅从交易状态推导出一个未提供的内部队列。希望沉淀的步骤是：先查询当单流水，再核对同一笔交易的处理状态与受理字段，满足条件才建议确认队列；仍需等待最终支付结果。

用 ORD-A1 作反例：一笔 600 成功，另一笔 400 处理中，但没有已受理字段。若候选把“处理中”统一改写成“进入确认队列”，它就把上一单的特定条件扩展错了。[payment_grader.py](../examples/capstone/payment_grader.py) 保留金额与状态评分，并检查队列建议是否由**同一笔交易**的两个字段支持。它还把“若以后确认受理，再进入……”与当前入队建议分别处理。

后台可能记住了规程，也可能没有修改方法。文件变动后还要阅读 diff：新步骤是否可用于别的订单，条件是否保留，支持文件是否一起更新。`real_review_revision` 表示取得了变更来源，不能单独证明方法质量或业务提升。

## 3. 六个阶段对应哪些函数和产物

主入口 [run_assembly_light.py](../examples/capstone/run_assembly_light.py) 的 `run` 创建 `LightAssembly`，依次执行六阶段。它继承 [run_assembly.py](../examples/assembly/run_assembly.py) 的编排，并替换逐题执行、采用增益条件和共享复测。原生 Agent 由 [foreground.py](../examples/assembly/assembly/runtime/foreground.py) 的 `make_agent` 创建，`run_task` 提取当前轮消息和实际工具记录。

| 阶段 | 当前代码 | 输入与更新 | 从哪里核对 |
|---|---|---|---|
| smoke | `Assembly.smoke` | 用基线方法查询 ORD-B1，先检查执行与付款结论 | `foreground.json`、`business_check.json`、配对工具回执 |
| learn | `Assembly.learn` | ORD-A2 查询与规程进入真实会话，观察原生后台复盘 | `background_result.json`、实例消息、后台工具回执与 Skill 文件 |
| candidate | `Assembly.candidate` | 从学习实例取得可用修订，调用 `create_candidate` 建隔离目录；对齐 frontmatter.name 时保留原文哈希 | `candidate.json`、`isolation.json`、`identity_adapter`、候选整树差异 |
| eval | `Assembly.eval`、`hermes_answers`、`decide`、`run.measured_decide` | 基线与候选分别执行四单主组和同订单新问法，评分后决定正式版 | 四份评测报告、`decision.json`、`execution.json`、`loaded_context.json` |
| shared | `LightAssembly.shared` | 采用版与候选分属不同本机共享组，各自在新的 Hermes 任务中复测 ORD-A2 | `sharing.json` 的组别、源文件、加载文件、模型确认与真实查询 |
| snapshot | `Assembly.snapshot` | 在独立方法副本上演练快照与恢复 | `snapshot.json` 与恢复前后的完整文件清单 |

表中的产物以每轮 `trace.json` 所记录的 evidence 路径为准，不能取不同轮的同名文件拼成一条链。候选来源依赖学习任务与后台记录，评测节点依赖候选与版本，采用决定再依赖评测节点。

学习实例中的后台可以修改它自己的教学 Skill。正式 `adopted/` 目录在候选生成和评测期间保持基线；`Assembly.install_adopted` 只接受可信 ADOPT，重新核对候选、决策和当前目录哈希，再切换整目录。候选没有可用修订时，代码可以复制基线继续评测，并记录 `real_review_revision=false`；这条路径没有发生方法进步。

## 4. 怎样区分运行完成、采用和提升

| 判断 | 必须看到的证据 | 可以作出的结论 |
|---|---|---|
| 产生候选 | 来源经历、实际后台动作、候选文件及内容差异 | 系统生成了可审阅更新 |
| 完成验证与决策 | 成对执行记录、可信评分、完整 checks、正式目录结果 | 本轮控制流程作出了有依据的决定 |
| 采用并重用 | ADOPT、正式目录与候选绑定、后续加载正文、配对工具回执 | 更新已经进入后续任务 |
| 在本批任务上改善 | 同协议的有效成对评分、预设增益条件、关键用例与复测通过 | 当前任务与协议下有测得的改善 |
| 推广到新条件 | 固定候选后执行独立的新订单或其它保留条件 | 支持相应范围的迁移判断 |

`completion.json` 的 `all_stages_finished` 描述六阶段是否完成。应继续读取 eval 的采用决定和正式目录哈希；流程正确拒绝候选时也可以完成后续共享检查与快照演练。REJECT 保持现版，是控制器的一条正常出口。

Capstone 在基础 `decide` 之外，通过 `run.measured_decide` 增加主组严格增益条件。基础 Assembly 策略允许完整可信且不劣的候选；两套标准应按实际入口解释。下面是 Capstone 的教学判断表，假定其它检查均满足：

| 主组基线 / 候选 | 决定 | 理由 |
|---|---|---|
| 3/4 → 4/4 | 可 ADOPT | 主组严格提升，候选关键要求全过，复测不退化 |
| 4/4 → 4/4 | REJECT | 本入口要求严格增益，相同通过率不足以更新正式版 |
| 3/4 → 3/4 | REJECT | 没有增益，且候选仍有关键题未通过 |
| 缺题、无有效回执或评分依据失配 | REJECT | 无法形成可信比较 |

第 18 章上一轮真实结果是 4/4 → 4/4，只支持“两套指令在这四题均通过”；该实验没有自动提炼并采用 Skill。不能将这个结果填入 Capstone 的成功更新栏。

## 5. 采用版如何影响下一次任务

`hermes_answers` 为每题新建进程、home 和会话，复制冻结的方法包，禁止后台修改被评 Skill。`worker` 将正文实际放进 `user_message`，同时记录 `loaded_context.json`。这证明该评测协议下的正文预载；应结合业务工具回执检查它是否改变了正确的判断或行动。

`LightAssembly.shared` 对正式采用版和隔离候选分别执行 push、pull、整树核对和独立 ORD-A2 查询。候选组用于复测，不会改变正式目录。若本轮 REJECT，正式组使用的仍是基线。回答措辞不同只能说明输出有差异，是否符合支付与队列条件还要用业务检查判断。

证据绑定中有两种本地哈希：`TaskRun.skill_hash` 与 `CandidateBundle.candidate_hash` 指向 SKILL.md 文件；`EvalReport.skill_hash` 与 `AdoptionDecision.new_skill_hash` 指向完整方法包。`trace.json` 中的 `hash_bridges` 保存两者映射。核对时先确认哈希对象，参考文件也属于方法版本。

当前主组与复测组是相同四笔订单的不同问法。[新订单保留题](../examples/capstone/new-order-reserve/README.md) 另备三笔改变金额与前置条件的订单，固定候选后再单独使用。当前主线只有一轮学习与验证；接收实例的新经历再次提炼并经过下一轮采用，尚未在本批真实运行中验证。

## 6. 每组课程在闭环中推进哪一步

| 章节 | 对自进化的作用 | 本组要回答的问题 |
|---|---|---|
| 01–06 | 建立可观察、可控制的执行与历史 | 当时任务看到了什么，做了什么，怎样保留调查状态？ |
| 07–09 | 提炼并加载方法，约束执行权限 | 候选怎样进入新任务，方法和工具权限如何分别控制？ |
| 10–14 | 衔接学习，保存和修订经验 | 复盘何时发生，事实与会话从哪里来，写入是否完成？ |
| 15–17 | 创建、增量更新和整理方法包 | 哪些经历值得保存，更新哪一项，哪些内容应保留或归档？ |
| 18–20 | 形成独立评分、数据集和搜索条件 | 候选改善了哪些业务条件，评分与生成是否隔离？ |
| 21–22 | 采集经历、生成共享候选并检查加载 | 谁贡献了什么，候选在哪个状态，第三实例实际用了哪版？ |
| 23 | 用受控巡检参考实现串联版本决策 | 评分缺失、无改善和恢复时，控制器怎样保持可信状态？ |
| Assembly / Capstone | 将原生执行、后台维护与采用控制接成一轮 | 经历、内容变化、成对结果、决定和后续执行能否逐项对应？ |

读完一章，先找到它改变的对象和实际决定更新的函数，再核对产物能证明的状态。进入综合实践后，按“经历 → 内容差异 → 成对评测 → 采用决定 → 实际加载 → 后续业务结果”阅读一轮记录。这样既能看清系统如何学习，也能准确定位它停在了哪一步。
