# 验证、运行与故障处置

## 无密钥工程检查

在仓库根目录使用 Python 3.12，开发环境与上游 Hermes 环境分开：

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python --require-hashes -r requirements-dev.lock.txt
make verify
make doctor
```

已有 Python 3.12 时也可用 `python3.12 -m venv .venv` 和 `.venv/bin/python -m pip install --require-hashes -r requirements-dev.lock.txt`。`make verify` 校验所有 Git 跟踪和待加入的 Python、Notebook 代码单元格、JSON/YAML、shell 语法，再运行 Ruff 和离线测试；不会执行 Notebook 的模型请求，不读取个人 `.env`。只有通过这些检查，才进入真实模型实验。

`make doctor` 显示解释器、直接开发依赖、四个上游工作区的完整提交及是否有改动。它只盘点本机，不访问网络。`model_execution_verified=false` 是盘点能力边界，不是一次模型错误。CI 对 macOS 和 Linux 执行相同离线检查；Windows 的文件锁/进程组暂未支持。CI 不提供模型密钥，也不运行 OS 沙箱或付费模型实验。

## 真实实验准备

1. 按 [根 README](../README.md) 执行 `bash scripts/setup_deps.sh`，记录四个上游的完整提交、环境版本与实际源码指纹。脚本获取默认分支，开发锁文件只锁离线检查依赖，不能据此声称真实运行可复现。已有目录不会自动更新。
2. 明确选择 Notebook、Hermes 模块化总装或 23 讲自建循环。使用对应解释器，保留各讲 README 的参数与版本要求；不要在多条路线之间复用未记录的输出。
3. 从环境提供自己的 `GLM_API_KEY`。部分原生脚本兼容 `BIGMODEL_API_KEY`，部分配置函数会在缺少环境密钥时读取 `~/.hermes/.env`；自动运行应显式设置环境，避免隐式个人配置。密钥不写入配置、命令参数或报告。
4. 企业数据题库先运行本轮评分与隔离探针。19 讲缺少 `/usr/bin/sandbox-exec` 时拒绝裸进程执行。Linux 上离线检查通过不表示企业运行沙箱已验收。
5. 使用全新运行编号与输出目录。保留失败记录；重试应产生新编号，不覆盖失败历史、不仅选择成功题。

从根目录执行 23 讲的真实实验：

```bash
export EVOLVE_JOB_TIMEOUT_SECONDS=900
.deps/hermes-agent/.venv/bin/python -B examples/23-final-assembly/final_assembly.py
```

该时限只约束一轮后台演化作业，不能约束整轮模型费用。调查预算由 `run_shift` 的参数控制，模型循环另有迭代与工具数上限。真实调用是否成功，以本轮原始回执和运行摘要为准。

## 证据核对顺序

| 证据 | 必须核对 |
|---|---|
| `source_manifest.json` | 运行前后源码与配置集合一致，包含共享执行代码和实际上游源码 |
| `review_input.json`、turn traces | 当前时刻查询、完整续班记录、正常停止、无工具错误；未决问题独立保留 |
| `eval_v0.json`、`eval_v1.json` | 两侧技能全文哈希、每轮实际技能哈希、用例集哈希一致；题目没有缺失或重复 |
| `eval_report.json`、`decision_log.json` | 原始裁判输出、自检、确定性重算及采用标准；缺失评分单列 |
| `versions.json` | 记录实际保留版、完整候选/采用内容哈希、前一有效内容和 UTC 时间 |
| `snapshots/<version>/` | 状态和技能同一清单；恢复前核验完整性；原库关闭后再恢复 |
| `step_08.json`、`run_summary.json` | 第三实例加载相同内容并成功实际执行、反馈完整；异常不得标记 COMPLETE |

23 讲输出位于 `examples/23-final-assembly/output/oncall-runs/<编号>/`。新增指纹与快照格式不能拿历史运行记录补足验收。本轮记录的 `COMPLETE` 也不等于已证明模型能力提升。

19 讲通过 `LECTURE19_OUTPUT_DIR` 指定每轮目录：用户配置保留，原生配置和绝对资源路径在当轮目录生成；`native-run-status.json` 逐步保存实际退出码。校验时限 120 秒、原生运行时限 4500 秒，内部沙箱 worker 默认 600 秒。超时记录退出码 124 和脱敏部分日志；作业失败使入口非零退出。

## 故障处置

| 现象 | 处置 | 继续条件 |
|---|---|---|
| 评分解析失败、结构损坏、缺题 | 保留原始结果，REJECT；修复解析/执行原因，不补分 | 全题及自检在新一轮完整执行 |
| 调查预算耗尽 | 停止当前工具读取，保留未决问题，复盘标为不完整 | 人工核对真实消耗后调整预算，重新运行 |
| 后台作业超时 | 核对取消结果和部分日志；不将超时当作无候选正常 skip | 上游故障/资源问题解除后用新编号运行 |
| 快照损坏或导入丢失内容 | 拒绝激活，原库保留；选择独立完整恢复点 | 哈希、会话、消息、完整性均通过 |
| 恢复遇到数据库忙 | 暂停所有写入方、关闭连接，保留原库与快照 | 无并发写入，确认目标目录属于当前实例 |
| 技能目录切换崩溃 | 暂停加载/写入；核验同级 `.restore-backup-*` 后恢复旧目录 | 技能全树哈希和加载行为验证一致 |
| 源码在运行中变化 | 阻止采用；保留当前结果作诊断 | 冻结新源码后重新运行，不能复用旧指纹 |
| 本地采用后共享发布失败 | 停止发布，保留本地与远端两侧版本证据 | 人工核对版本后补偿；本仓库尚无分布式发布事务 |
| 第三实例执行失败 | 运行记为 INCOMPLETE，保留已经作出的决策 | 加载、工具执行和反馈独立验证完成 |

不要手工删除正在使用的 SQLite WAL/SHM，不要把整个会话库时间点恢复当作日常 Skill 回退。新快照清单是完整性证据，需要受控存储；有人能同时改写文件和清单时，哈希不能提供身份认证。

## 走向业务落地的验收顺序

先接一项只读业务工具，明确租户/对象/时间窗口和结果契约；建立现有服务基线、独立保留集、已知错误样本与评分器自检。用影子运行记录任务正确率、硬错误率、工具错误率、无效评分比例、请求成本和耗时。错误、预算耗尽、评测拒绝都应进入分母。

候选生成和发布应分权：学习端只写候选，评测端冻结代码/数据/参数，发布端只接受有效决策和对应内容哈希。补齐发布锁、条件写入和失败补偿，再验证第三实例实际加载。灰度比例和回退触发阈值由业务负责人根据风险确定；四题或六题演示不承担统计显著性或生产非劣效证明。

验收应分别记录：真实上游兼容、OS 读写/网络隔离、模型工具循环、后台不中断前台、候选隔离、业务回归、发布一致性、恢复演练、跨主机分发。离线通过只代表当前工程回归通过。
