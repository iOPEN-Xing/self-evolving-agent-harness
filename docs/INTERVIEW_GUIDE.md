# 项目面试指南：把机制讲成有证据的工程选择

我的判断是，这个项目最值得讲清的是：执行经历如何变成候选方法，系统为什么可以拒绝更新，以及下一次任务怎样用到实际采用的版本。框架名称帮助定位实现，设计取舍与证据才说明理解深度。

本次依据用户本地 `romain-skill` 的核心模型、面试准备、技术路径和来源索引，应用“为什么做 → 怎么做与取舍 → 结果与证据”的项目讲述方法。参考其高覆盖的项目准备原则，以当前仓库代码约束技术主张；没有把求职笔记作为本项目实验结果，也没有照搬其中个人经历。

本轮覆盖原有 42 份 Markdown 和 9 份 Notebook 的阅读内容。章节各自补入对应案例的讲述与追问；工程文档解释决策、故障和验收；历史报告保留原轮次范围。供模型执行的 payment-report Skill 按核查步骤优化，保持原字段与判断语义，面试叙事留在其章节文档。新增本页后共 43 份 Markdown。

## 先明确个人工作与项目范围

下文第一人称用于练习项目表达。基于这个 fork，可以介绍自己完成的工程化整理、代码复核、回归修复、模型接入与文档对应工作；上游的 Codex SDK、Hermes、SkillClaw、GEPA 和课程原始实现保留归属。讲一个实验时，明确自己实际运行、阅读或修改了哪部分，再引用对应记录。

已有资产是可阅读代码、构造业务题、离线回归及选定真实模型记录。这里按大模型开发或 Agent 工程岗位准备讲述；具体岗位、个人分工和投入时间尚未补充，不编造上线经历、业务规模、性能提升或准确率增益。

## 60—90 秒总述示例

“我基于一套开源 Agent 课程做了工程化整理，关注经验更新能否可靠地影响后续任务。一次支付查询会留下真实工具记录，后台据此生成 Skill 候选；候选先隔离，再和基线按固定业务条件比较，满足采用策略才进入正式目录，接收任务还要核对实际加载。

我的整理重点是把失败边界和证据补齐：例如快照损坏时保住原库，评分缺失时拒绝采用，文档里的函数和 Notebook 摘录要对应真实代码。支付案例特别检查处理中的交易不能算到账，内部队列建议要有同笔渠道受理及规程来源。

当前能讲清的是 Skill 层一轮受控更新的机制和已验证的工程行为。四题指令对照此前是 4/4 到 4/4，没有测得增益；新订单检验和持续第二轮还需要接线与运行。要走向生产，我会先用只读影子任务建立更大独立题组，再验收发布一致性和失败补偿。”

讲述后准备打开 [工程复核](ENGINEERING_REVIEW.md)、[实际迁移结果](DOCUMENTATION_VALIDATION.md) 与 [自进化函数及产物](SELF_EVOLUTION.md)。不要用架构图代替尚未取得的运行结果。

## 深挖一笔付款，比罗列组件更有用

ORD-A2 应付 800，TXN-X 为 processing，且 channel_acceptance 为 success。工具给出这两项事实，用户提示另给内部规程：这组条件可进入 payops-confirm-17。规程来源是 [POLICY](../examples/assembly/run_skillclaw_demo.py)，订单来源是 [orders.json](../examples/assembly/scenarios/orders.json)。

“为什么做”：渠道受理与最终到账不同，误判会产生错误状态或队列建议。“怎么做”：查询同一笔交易，保留条件生成方法，再用 ORD-A1 的部分成功、部分处理中但未提供受理字段作反例。“怎样验收”：检查候选差异，固定完整方法包，对基线与候选独立执行并评分，沿采用决定核对后续加载。

这里的关键取舍是允许不更新。Capstone 的主组严格增益条件会拒绝平分候选；基础 Assembly 使用可信且不劣条件。对应入口分别是 [run_assembly_light.py](../examples/capstone/run_assembly_light.py) 的 `run.measured_decide` 与 [policy.py](../examples/assembly/assembly/eval/policy.py) 的 `decide`。不能混用两个标准解释同一个决定。

## 追问要回答到检查对象

| 追问 | 回答依据与判断 | 还应主动说明的范围 |
|---|---|---|
| 为什么不直接改提示词？ | 后台按经历生成候选，独立评分限制错误概括；`Assembly.candidate` 与正式目录分开 | 用户给出的规程仍是外部输入；不能把所有知识都算模型自主发现 |
| 为什么不只存 Memory？ | 事实与偏好适合 Memory，条件、步骤和参考资料适合 Skill；Session 保存执行依据 | 对象保存不证明真实性，也不保证新任务召回 |
| 自进化体现在哪里？ | 经历 → 实际修订 → 成对评测 → 采用 → 后续加载与工具执行 | 候选生成、有效更新、效果提升和持续下一轮各需证据 |
| 比简单规则引擎好在哪里？ | 模型可从非结构化经历归纳候选，控制器以固定规则验证与发布 | 本批没有证明它胜过规则引擎；稳定可枚举业务规则应保留确定性实现 |
| 怎样防止学错？ | 固定输入与评分，加入旧能力、新条件、信息缺失和错误样本；不合格保留基线 | 小样本不能证明长期安全；评分器也需自测和语义审阅 |
| 有什么实际结果？ | 明确引用所选轮次的回归、真实请求与业务评分；4/4 → 4/4 如实讲没有增益 | 未运行的新订单与第二轮没有结果，生产收益没有证明 |
| 线上成本与延迟如何？ | 记录实际模型请求、usage、工具耗时、后台时限；阶段任务数与 HTTP 次数分开 | 当前没有整套生产成本测量，供应商账单与 token 代理指标不同 |
| 采用后仍出错怎么办？ | 核对正式内容与实际加载，再定位方法、数据、工具或评分变化；恢复已核验方法包 | Skill 回退保留 Session，不自动撤销外部业务；远端发布需要补偿 |
| 多实例共同学习验证了吗？ | 本机采集与共享可以逐项核对来源、发布、下载、加载和行为 | 重复快照不是独立样本；跨主机一致性与接收实例第二轮学习尚未验收 |

## 如何把“效果不错”改成可检查的结果

| 容易被问穿的表达 | 与当前代码和证据对应的表达 |
|---|---|
| 系统自动持续进化 | 当前综合入口执行一轮；候选来自原生后台的路径可核查，下一轮仍需验证 |
| 修改了 Skill，所以能力提高了 | 保存了候选差异；改善必须依据固定协议下有效成对评分，采用后再检查使用 |
| 测试全部通过，项目可以上线 | 离线验证覆盖工程行为；真实模型、OS 隔离、发布和业务验收另行记录 |
| 正确率大幅提升 | 已有四题指令对照两版均通过，没有测得增益；不编造更大样本结果 |
| 跨实例共享已经完成 | 本机对照区分下载与实际加载；跨主机故障与生产一致性尚未验证 |
| 使用了官方 GEPA，产生赢家 | 先查看官方赢家身份；教学送检提案和采用资格分别记录，脚本保持正式基线 |
| 完成了全自动生产回滚 | 方法副本恢复与会话历史恢复各有范围，外部业务补偿及分布式事务尚未实现 |

## 用追问形成自己的准备闭环

先选择一个你实际修改或验证的案例，录一段短讲述。围绕背景、输入质量、简单基线、设计取舍、坏例、成本、恢复和下一步连续追问；答不清的地方先回查实现与记录，再修改表述。每次只补有证据的内容，尚无结果的指标列入下一次实验计划。

可用练习指令：“请根据本仓库与我的实际工作记录，连续追问为什么这样设计、替代方案、坏例和验收边界。要求我指出函数、输入与结果来源；缺少证据时帮我缩小主张，不帮我编造指标。”

各章的“面试讲述与追问”提供不同的切入点。完成一次练习的标准是：能给出明确判断、解释取舍、打开依据，并说明什么条件改变后结论不再成立。
